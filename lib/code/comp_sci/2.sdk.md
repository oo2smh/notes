# 🐧 Tldr
- **What**: SDK is the downloaded bundle of code needed to prep/run a language. It is often bundled in a `language install` with the `toolchain`: additional tools (pkg/venv manager) to boost a language.
- **Why**: Gives you a better understanding of how the code is ran which allows for better debugging.
- **How**: By going over the SDK as it is being ran, detailing the processing of language prepping (lexing/parser) and running.

- 🎯 SDK has 2 main phases. `frontend compilation` and `runtime execution`. The runtime focuses mainly on stack management. Stack management has 2 phases associated with it 1. creation phase, 2. execution phase. During these phases the `stack frame` is created. The anatomy of a stack frame will be covered. 2 topics associated with stack management: variable resolution and closures will be covered.

# 💀 Anatomy of the SDK
> [!note] The `backend translator` is the pivotal way to define the language when it comes to compiled vs interpreted languages. It answers how does the code run?

1. `Frontend compiler`: Compiler that preps the code (lexing, parsing)
2. `Back-end translator`: Either an interpreter/compiler.
  - If it's an `interpreter`, then the translator is bundled with the runtime
  - If it's a `compiler`, then it performs a 2nd compilation from intermediate to machine code.
3 `Runtime`: All code used during the `running` or execution of code. Code bootstraps a RAM process, sets up memory and provides Std lib hooks.
  - `Bootstrapper`: code to initialize the sandboxed region.
  - `Engine`: The main code runner. Either a VM. Or for compiled lang, it's the CPU itself.
  - `Linker/Loader`: Std API. Prewritten code. Typically called the Standard Library. Some modules are baked into the interpreter/compiler and requires no imports. This is done for convenience and speed. Others are split into modules and requires importing before use. This is linked and loaded via the linkers/loaders.
    - ✏️ js: All modules are baked in. No imports
    - ✏️ py/go: Hybrid some are baked into the `builtin(s)` package or module. The rest require imports to be used.
  - `Memory Manager`: Starts stack/heap manager. Garbage collector
  - `Scheduler`: Manages the order of operations. Call stack order and the event loop.

# Frontend Compilation
> After frontend compilation, transformed code is returned. For interpreted engines, this is preprocessed code and in many cases intermediate bytecodes. For compiled languages, this is machine code that the cpu can run.

> [!note] When frontend compilation happens, the OS creates a process. For interpreted languages, only one process is created for frontend compilation and runtime. This can be called a super-process. For compiled languages, 2 separate processes are created.

## *LEXING (TOKENIZATION) 🧩*
- Source code is broken down atomically into `tokens`. Syntactic breakdown into parts of speech: nouns, verbs, adjectives, etc.
  - Tokens include: operators, literals, invisibles, keywords.

## *PARSING (STRUCTURING) 🏗️*
1. Syntax parsing
  - Tokens are further structured and grafted onto the `AST: Abstract syntax tree.`
2. Semantic Parsing
  - Type checking: Are types valid?
  - Scope resolution: A `Symbol Table` is created. Within the symbol table, there are subtables for each scope: global, function, block.
    - It is discarded for compilers, but remains persistent for interpreter engines. For interpreter engines, the symbol table at this time only differentiates between global and local and later on fills in the details.

# Runtime
> The runtime is the bundle of code that aids or directly influences the execution of code. There are many modules of the runtime.

```yaml
Bootstrapper: Asks the OS for a process and creates the env.
Linker_Loader: Maps `prebuilts` to RAM immediately. Fetches `modules` from disk only when imported.
Memory Manager: Subdivides the process into stack/heap. Starts the garbage collector in the background thread.
Scheduler: As the code is ran, it keeps track of the currently active code. It pops off inactive code from the stack. It runs the event loop. It also manages concurrency.
Executor: Either the CPU or the interpreter engine. Runs each line of code.
```

## *STACK ALLOCATION*
- When the engine boots up and starts, it pushes the `Global frame` to the stack. This will hold the global variables, environment variables, and the shutdown return so it knows when to exit the program.
- There are 2 phases of stack allocation
  1. Creation phase
  2. Execution phase

> [!note] Global frame is also called entry frame and main frame. JS calls the stack frame an execution context!

## *STACK FRAME ANATOMY*
- As the executor meets a function, it will be added to the stack. Each frame stack holds pertinent info to run the function.

```yaml
Arguments
Return Address
Local variables
Reference to outer env: Used for scope chain (interpreted languages)
```

## *JS FRAME STACK IMPLEMENTATION*
```js
const callstack = [];

// FEC
const stackFrame = {
  parameters: {0: username, length: 1},
  arguments: {0: 'eddy', length: 1},
  returnAddress = 14; // line # where fn is invoked
}

const fnExecContext = {
  lexicalEnvironment: {
    environmentRecord: {
      'arguments': {0: 'eddy', length: 1}
      username: 'eddy'
      personalGreeting: function() {
        console.log(`Hello ${username}`);
      }
    }
  }
}

// GEC
const initStackFrame = {
  parameters: null
  arguments: {length:0}
  returnAddress = 0; // line # where fn is invoked
}

const globalExecContext = {
  lexicalEnvironment = {
    environmentRecord: {
      x: 10,
      y: 20,
      greeting: function(username) {
        console.log('Hello.');
        function personalGreeting() {
          console.log(`Hello ${username}.`)
        }
      }
    },
    variableEnvironment: {
      z: 30
    },
    outerEnvironment: null,
    this: 'Global Object'
  }
}

callStack.push(stackFrame, fnExecContext);
```

## *VARIABLE RESOLUTION*
> [!note] Variable resolution happens during execution

- Python has `LNGB` dicts in the heap. It searches 4 dicts and stops when it finds the variable it is looking for. `locals()`, `nonlocal`, `globals()`, `__builtins__`
- JS travels through the `lexicalEnvironment.outerEnvironment` to resolve variables
- Go and other compilation-based languages resolves variables during `front-end compilation` using the symbol table.

## *CLOSURES*
> A closure is a function wrapped with the reference to its outer scope.

### Javascript
- A closure is created during the creation phase. It is closed over during the execution phase.

### Python
- Python uses a special attribute called `__closure__`, a tuple.
- `__closure__` holds elements & each element is a `cell object`.
  - `cell object`: This object is of type `cell`. The `cell` object has a `cell_contents` attribute. The cell object holds `references` to the function and the affected outer-scope variables wrapped as a cell object.

### Go
- Under the hood, a Go closure is a function pointer paired with a pointer to the environment (the captured variables).
