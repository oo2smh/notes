# Intro
- Intentional removal of digital barriers to ensure people with disabilities can perceive, understand, navigate, and interact with the web.
- The Numeronym "a11y": Represents the 11 letters between the 'a' and 'y' in "accessibility."
  - The "Ally" Connection: While "a11y" looks like "ally," ensure your choice of typeface distinguishes between the number 1 and the letter l for better readability.

## *ACCESSIBILITY VS. INCLUSIVITY VS. USABILITY*
- `Inclusive Design`: A broader methodology that considers all human diversity (age, language, tech literacy, etc.). Accessibility is a necessary outcome of inclusive design.
  - `Accessibility`: Equal access for people with disabilities (e.g., screen reader compatibility).
  - `Usability`: Measures how effectively and efficiently a user can achieve a goal. A site can be technically "accessible" (code-compliant) but "unusable" (frustrating or confusing).

## *THE REACH OF ACCESSIBLE DESIGN*
- Accessibility features often provide "curb-cut" benefits—solutions designed for disability that help everyone:
  1. Captions: Vital for the Deaf community; also used by people in noisy environments or those learning a new language.
  2. High Contrast: Essential for low vision; also helps anyone using a phone in bright sunlight.
  3. Keyboard Navigation: Required for motor disabilities; also preferred by "power users" for speed.

## *CATEGORIES OF DISABILITY*
- Disabilities are not always permanent or visible. They generally fall into four categories:
  1. Visual: Blindness, low vision, color blindness.
  2. Mobility: Paralysis, tremors, limb loss.
  3. Hearing:
  4. Cognitive: Dyslexia, ADHD, memory loss.
  5. Perspective: Disabilities can be Permanent (born with one arm), Temporary (a broken wrist), or Situational (holding a baby with one arm).

## *ASSISTIVE TECHNOLOGY (AT)*
- AT is any tool used to bridge the gap between a user’s capability and a digital barrier.
- Common Web AT: Screen readers (speak text aloud), screen magnifiers, voice recognition (navigating by speech), and switch controls.
- Crucial Note: Having the AT does not guarantee access. If the code is poor, the AT cannot "read" or "interact" with the site correctly.

# WCAG Overview
- `Web Content Accessibility Guidelines (WCAG)`: Guidelines that comply with accessibility standards. Scope: It covers design, content, and code.
- Consists of Theory (Principles/Guidelines), Criterias (78), Grading System (A, A, AAA)

## *EVOLUTION & VERSIONS*
- WCAG 2.0 (2008): Introduced the `POUR principles`. Focused on being technology-neutral (not just HTML).
- WCAG 2.1 (2018): Adds 12 new `criteria`, specifically targeting mobile devices, low vision, and cognitive disabilities. Backwards compatible with 2.0.
- WCAG 2.2 (2023): Further extensions for mobile and cognitive accessibility.
- WCAG 3.0 ("Silver"): Future major overhaul (currently a draft). It aims to be even more inclusive across various "Web of Things" devices.

## *THE P.O.U.R. PRINCIPLES*
- 4 principles are POUR. Each principle is followed by guideline(s). 13 total guidelines.

1. `Perceivable`: Users must be able to see or hear the content (it can't be "invisible" to their senses).
  - 1.1 Text Alternatives: Provide text alternatives for any non-text content (like images).
  - 1.2 Time-based Media: Provide alternatives for video and audio (like captions).
  - 1.3 Adaptable: Create content that can be presented in different ways without losing information (like a simpler layout).
2. `Operable`: Users must be able to interact with the UI (e.g., keyboard-only navigation).
  - 2.1 Keyboard Accessible: Make all functionality available from a keyboard.
  - 2.2 Enough Time: Provide users enough time to read and use content.
  - 2.3 Seizures and Physical Reactions: Do not design content in a way that is known to cause seizures.
  - 2.4 Navigable: Provide ways to help users navigate, find content, and see where they are.
  - 2.5 Input Modalities: Make it easier for users to operate functionality through various inputs beyond just a keyboard (like touch or pointers).
3. `Understandable`: Both the content and the UI mechanics must be clear.a
  - 3.1 Readable: Make text content readable and understandable.
  - 3.2 Predictable: Make web pages appear and operate in predictable ways.
  - 3.3 Input Assistance: Help users avoid and correct mistakes.
4. `Robust`: The code must work across various browsers and assistive technologies (AT), now and in the future.
  - 4.1 Compatible: Maximize compatibility with current and future user agents (browsers and screen readers).


## *GRADING SYSTEM*
> 78 total success criterias(SC)

1. A: The Floor.  Pass all 30 Level A.
2. AA: The Standard. Pass all Level A PLUS all 20 Level AA.
3. AAA: The Ceiling. Pass everything in A and AA PLUS the 28 Level AAA.

### A Examples
- providing alterative text for images
- making sure color is not the only means used to convey information (for example, including an icon within an error message for colorblind users)
- ensuring all functionality of the content is operable through a keyboard (because not all people can use a mouse device to navigate the Web)
- ensuring links have clear labels that clearly indicate their purpose
- providing shortcuts on the page to allow users to bypass repeated sections of content across pages
- providing captions for pre-recorded audio content

### AA Examples
- ensuring a more readable contrast between text and background colors
- ensuring the content can be accessed on various devices
- ensuring that the page content is implemented in a way that does not prohibit page zoom
- providing clearly visible focus indicators so that keyboard users can identify their current whereabouts on a page
- properly conveying page structure using appropriate descriptive headings and labels

### AAA Examples
- ensuring all functionality of the content is operable through a keyboard interface without requiring specific timings for individual keystrokes
- ensuring a higher color contrast than that required in Level AA
- allowing the user to disable animations triggered by interactions
- ensuring interactive elements have target sizes large enough for users to easily activate them
- ensuring users can understand abbreviations by giving them access to the expanded form of those abbreviations

# WCAG Compliance Does Not Mean Usable!
- This section highlights a critical industry truth: Compliance is not the same as accessibility. While WCAG provides the legal and technical "floor," true accessibility is about the human experience.

## 1. The "Compliance Gap"
- You can technically pass a WCAG audit and still have a website that is impossible to use.
- The Level AA Trap: If you only meet Level AA, you might still be excluding users who need Level AAA features (like expanded abbreviations or specialized contrast).
- Technically Correct, Humanly Wrong: A site can have a valid focus indicator (meeting WCAG), but if that indicator is faint or disappears too quickly, a user with low vision or ADHD will still lose their place.
- WCAG focuses on whether the code is "programmatically determinable." Usability focuses on whether a human can actually complete a task efficiently.
- Unexpected Interactions: WCAG might require a component to be keyboard-accessible, but it doesn't always specify which keys. If you use non-standard shortcuts, users will be lost.
- Content Complexity: You can have perfectly accessible code surrounding text that is written in such a complex way that it excludes people with cognitive or learning disabilities.


## The Solution: Usability Testing
> "Think of accessibility as the lowest bar; it works with assistive technology, but to go beyond ‘it works’ to ‘it’s enjoyable and easy to use’ you’ll need to test with real users." — Kate Kalcevich

- The only way to bridge the gap between compliance and true accessibility is to test with disabled users.
- Automated tools only catch ~30% of issues.
- Manual WCAG audits catch more, but they don't account for browser bugs or how a person with a lived disability actually navigates a screen at 400% zoom.

## From HTML to the DOM to the Accessibility Tree
- When a browser loads your page, it creates two primary structures in parallel:
  1. `The DOM Tree`: A complete representation of every HTML element (<div>, <span>, <head>, etc.). This is combined with CSS to paint the visual UI.
  2. `The Accessibility Tree`: A subset of the DOM tree. It filters out "generic" elements that don't add meaning (like styling-only <div>s) and focuses only on elements with semantic value.

## The Four Pillars of an Accessible Object
- For every element included in the accessibility tree, the browser exposes four critical pieces of information:
  - Role: What is it? (e.g., button, link, heading, checkbox).
  - Name: What is it called? (e.g., the "Submit" text on a button).
  - Description: Extra context (e.g., "Password must be 8 characters").
  - State: What is it doing right now? (e.g., checked, disabled, expanded).

## 3. How the Tree is Built
- The information in the tree is determined by three factors:
- Semantic HTML: Using <button> instead of <div> gives the element an automatic "implicit" role.
- ARIA Attributes: You can use ARIA to explicitly define roles, states, and properties if native HTML isn't enough.
- CSS Styles: Properties like display: none or visibility: hidden will remove an element from the accessibility tree entirely.

## Inspecting the Tree
- Open Browser DevTools (F12).
- Select an element in the Elements tab.
- Look for the Accessibility sub-tab (usually next to "Computed" or "Styles").
- Here, you can see the computed Name, Role, and any ARIA properties currently active.
- Key Takeaway: Screen readers rarely interact with the DOM directly; they rely on the Accessibility Tree. If an element isn't in the tree—or if it's there with the wrong Role or Name—it effectively doesn't exist for a screen reader user.

## Different, but Lookalikes
- button vs links: Buttons are for actions. Anchors are for navigation (to heading or another pg).
- article vs aside:
  - <article>: Independent content. If you ripped it out of the site and put it on another page, it would still make sense (e.g., a blog post, a news report, or a forum comment).
 - <aside>: Indirectly related content. It’s "tangential." If you removed it, the main content would still be complete.
- nav vs menu
  - <nav>: A wrapper for major navigation blocks (the header menu, footer links, or a table of contents). It tells screen readers, "This is how you move around the site."
  - <menu>: Semantically, a list of interactive commands. Use this for toolbars or context menus (e.g., a "File/Edit/View" menu in a web app).

- Easy to see. Can help a person judge where they are. Header, footer, main.

# ARIA
- Accessible Rich Internet Applications.
  - ARIA is a supplement! Use minimally.
- Web standard that extend HTML to add semantic roles, states, and properties to be better understood by assistive technologies
- `Affordance`: quality or property of an object that defines its possible uses and clarifies how it can or should be used.
  - ARIA creates semantic affordances. Styling provides visual affordances for sighted users.

## ARIA Label vs Name
- Label: text that is presented visually
- Name: text that a screen reader reads aloud. Usually called "accessible name" to make this distinction clear.
- These should be ideally linked.

> [!note] Not all elements need an accessible name. Interactive elements require an acc Name. Others could be enhanced by an acc Name. Some should not have acc names. (p, caption, mark, time)
- Generic containers or roleless elements should not have an acc NAME! No acc name on divs or spans.

aria-label and aria-labelledby have similar behaviour in screen
readers and the Accessibility API, but aria-label should be reserved
for when there is no visible text on the page to reference or when keeping
track of id values would be too difficult.

— The Using ARIA document


## ARIA Attributes Anatomy
1. Roles: Mostly covered by semantic html
2. States: prefixed with aria-
  - aria-pressed="true", aria-expanded="false"
  - user interacted and mostly tied to js
  - best practice to add aria states from your js
3. Properties: prefixed with aria-
  - aria-label, aria-labelledby, aria-haspopup

## Roles
1. `Abstract`: roles that other roles are built upon. Not meant to be used in content.
2. `Landmark`: key areas of a page.
3. `Document structure`: Roles that describe structure of a page. Headings, articles, lists. Image.
4. `Widget`: Tabs, switches, menu, interactive components
5. `Live Region`: Blocks whose content updates dynmaically.
6. `Window`: Windows within the page. Example: main, modal dialog, tooltip.

## Rules
- Finite. You can't make up your own roles.
  - Use aria-propretiy `aria-label` or `labelledby` instead.
- Aria does not add behavior.
  - Aria is a promise. After you change the role, you have to add the expected behavior.

# Best Practices
## General
- use `all: unset` to clear all browser styles on a selector
- use aria-label only if you can't use visually-hidden

## Site Navigation
-  Use li within nav to give screen readers the total amount of links
- Use `aria-current=page` to indicate the currently selected page
  - Use styling with attribute selector to style current element
- nav > li should have role="link"
- Don't add "Navigation" to the aria name

## SVG Aria
- use span inside with text and add visually-hidden class
- the most robust method currently
- If svg is decorative use aria-hidden="true"
- It's good to avoid using aria-label if you can

## Alt text for Images
- logo alt text should describe the destination not contents
  - "Exchange Church - Home"
- Use empty alt if the image is decorative or unessential
-describe function of img and not content
- alt is for purpose. Not for attribution. Use figcaption for attribution.

### Informative Images
- Alt text. Short and concise. But as long as it needs to be.
- 125 characters max. Enter the alt text with a period. Don't mention it's an image.
Only detail why it matters. Emotion matters.


## Use the Right Aria
- Do not use heading aria on a button!
  - buttons are interactive elements, not headings (static)
- Tab list should always be a child in a `tablist` role

## Nonsupported Components
- Use Aria. Composite role.
  - EX: Tablist, talist, tab, tabpanel

## Hiding Content
### The Heavy Hitters (Used Daily)
1. display: none; and the hidden attribute
  - These are the industry standards for hiding content that shouldn't be there at all—like a mobile menu when the screen is wide, or a modal that hasn't been clicked yet.
    - When to use: Tabs, Modals, Accordions, and Responsive Navigation.
2. visually-hidden class
  - This is the "pro move" for accessibility. It keeps text on the page for screen readers but hides it from sighted users.
  - When to use: Adding a "Search" label to a button that only has a magnifying glass icon, or providing instructions like "opens in a new window."
3. aria-hidden="true"
  - Essential for decorative items.
  - When to use: Font-awesome icons or SVGs that sit next to text. If you have a "Home" link with a house icon, you hide the icon so the screen reader doesn't say "House, Home."

### The Functional Controllers
1. disabled and inert
disabled: Used strictly for form inputs (buttons, inputs) to show they aren't ready yet (e.g., "Submit" is grayed out until the form is valid).

2. inert: A newer but extremely powerful attribute. It makes an entire section of the page "dead"—no clicking, no tabbing, no screen reading.
  - Real-life use: When a Modal is open, you put inert on the rest of the website behind it so the user can't accidentally tab into the background.

## LANDMARKS
- You can create your own landmarks (wrap the content in a <section> element (or an equivalent element with an explicit role="region"), and
give the section an accessible name.)
- use as few landmarks as possible, but ensure that all of the content on the page is contained within a meaningful landmark region.

## NAMING
- Use id to hook up names in aria ( also the same for label )
- 2 main naming strategies. Span or Heading.
  - Usually use heading if you will show the text and span if you plan on hiding the text.
- No need to call something the tag name like img (redundant b/c screen reader says it)
- Call main nav (Site)
- All interactive elements must have an accessible name (all input)
- So if you add a string of text to an element using CSS ::before or ::after pseudo-elements, for example, this string of text is going to be included as part of the accessible name of the element.
-  But you generally should not use the title attribute to provide accessible names to elements. The only exception to this is <iframe>s:
- The aria-labelledby attribute is used when the text you want to use as an accessible name is already present elsewhere on the page.
  - At this point it is worth mentioning that when aria-labelledby is used to provide an accessible name to an element, it takes the highest priority over all other naming techniques when the browser computes the accName of an element.
- The aria-describedby attribute is similar to aria-labelledby, except that it is used to provide an accessible description (accDesc) to an element instead of an accName. It also accepts one or more IDs of elements that together provide an accDesc to the element it is used on.
- `aria-labelledby` can get names from multiplei sources.  aria-labelledby="id_1 id_2">
- A best practice is to have the text of the label at the start of the name.

### Hierarchy of Names
1. Use HTML content (such as text in a <a> or text in a <button>).
2. Otherwise, use an HTML attribute or element (such as alt or <label>).
3. Otherwise, use aria-labelledby referencing an element that’s already in the page.
4. Otherwise, when none of the previous methods is possible, use aria-label.

- One way to think of alternative text is to think about how you would read the page containing the image to someone over the phone, without mentioning that there is an image present. Whatever you say instead of the image is typically a good start for writing the alternative text.
- Keep it short

- A <figcaption> represents a caption that describes the contents of its containing <figure>. If the <figure> contains an <img>, the caption would provide an additional description that is usually meant to relate the image back to the context in which it is used.
